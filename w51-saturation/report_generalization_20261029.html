Turning the W51 saturation recovery into a package for other JWST programs¶

This report discusses how the process that restores saturated pixels in the W51 images could become a Python package that works on other JWST imaging programs. Programs differ in instrument, filters, number of filters, readout settings, dithers and targets. A package therefore has to find out from each dataset which methods can run and whether their results can be trusted there.

How it was made. Four agents each read one part of the code and wrote a proposal: the detector methods (response curve, first read, refit), the star models, the cross-filter fill, and the structure of the whole process. A fifth agent reviewed the four proposals, settled where they disagreed, tested them against four other kinds of programs and ordered the work. The agents read code and READMEs only; nothing was run or changed. The numbers come from the project READMEs and earlier reports, and I checked the ones in the figures against the READMEs. Effort estimates are the agents' guesses.

Short answer.

  • General as is: the NIRCam first read, the refit of pixels the pipeline skipped, the census of saturated pixels, the merge, and the checks.
  • General, refit on each program's own data: the MIRI response curve and level-1 correction, and the star model (PSF fits to the wings, and the predictor trained on them).
  • Depends on what was observed: the cross-filter fill. It needs at least three well-spaced filters and must pass a hold-out test on the new data before it is used, which is your proposal made concrete (section 2).
  • Specific to W51: the SOFIA pin (it becomes an optional plug-in for any unsaturated, lower-resolution image of the same sky), the MIRI coronagraph panes and Lyot field, and the hand-set filter order and constants.
  • First release: the methods that need no training, plus the self-tests that decide trust. Then the response curve and the star model. Then the cross-filter fill.

Glossary

term meaning
saturated pixel a pixel that collected more charge than the detector can record; the pipeline gives it no value
group the detector is read several times during an exposure; a group is one such read (on NIRCam the average of several frames)
first read NIRCam's first frame of an exposure (ZEROFRAME), often below saturation when later groups are not
response curve how a pixel's recorded signal grows as it fills; read backwards, it gives the brightness of a pixel that saturated after its first group
level-1 correction a MIRI pixel with one good group gets its value from that group alone, about 15% low; the correction removes this bias
PSF point spread function: the shape of a star on the detector, computed with STPSF
star model the core of a saturated star predicted from its unsaturated wings using the PSF
cross-filter fill the brightness of a saturated diffuse region predicted from the same sky in other filters
anchor an image of the same sky that did not saturate, from another telescope, used to set the level of a fill (SOFIA in W51)
self-test a test the package runs on each new dataset to decide whether a method can be trusted there
hold-out test pixels with a known value are hidden from a method and predicted, to measure its error
extrapolation factor how much brighter a restored pixel is than the brightest pixel the method was trained on
dex a factor of 10 in log; 0.1 dex is 26%
sidecar file a separate file next to the pipeline's file, holding the restored values
stage 3 the JWST pipeline step that combines exposures into a mosaic

Where the agents disagreed, and what the reviewer found.

  • Does the JWST pipeline already use the first read? Its default ramp fit does not restore a pixel saturated in its first group (stcal ols_fit.py only slices the ZEROFRAME; suppress_one_group is on by default in ramp_fit_step.py). An optional fitter (likely_fit.py) does use the ZEROFRAME; whether it restores such pixels was not checked. The first-read method stays in the package.
  • Is the star model a PSF fit? The production values (methods 5 and 7) come from a trained predictor (ridge line plus quantile trees, train_model.py), trained on PSF-fit labels. PSF fitting is general; the trained predictor depends on the readout and needs retraining per program. The package keeps them as two parts.
  • The NIRCam response curve was valid only up to 1.25 times the saturation charge and never ran in production. It stays out.

2. How the package decides what to trust¶

Each method declares three things: the data it needs, the kinds of saturated pixels it may fill, and a self-test. When the data are missing, the method does not run (a program with one filter has no cross-filter fill). When its self-test fails on the new data, its values are left out or marked low confidence, and the next method in the order gets the pixel. When no method passes, the pixel stays empty and is listed as not restored. The table in appendix A lists each self-test with its proposed pass rule and the W51 value it was rounded from.

Your proposal for the cross-filter fill: trust it below a validated spread. The reviewer found it sound as a gate, with one weakness: every available truth is fainter than the real cores. The figure shows the error of the MIRI fill in W51 at three distances beyond its training range (the brightness-band test: train on pixels below 1/8 of the brightest, predict the brighter ones).

Reading. The error grows with distance beyond the training range. F770W and F1280W stay below 0.10 dex up to 8 times the brightest training pixel. F2100W crosses 0.10 dex at 2-4 times (W51 pins it to SOFIA for this reason). F1000W lies 0.155 dex low at 2-4 times, so under the rule below its fill would be switched off. Most fills lie inside the tested range: no F770W or F1000W fill lies beyond 8 times, and 1.8% of the F1280W fills do. Before the SOFIA pin, 25% of the F2100W fills lay beyond 8 times and 14% beyond 16 times.

The rule the reviewer proposes, per feature set of the fill:

  1. Trusted: at 2-4 times, |bias| at most 0.05 dex and half-width at most 0.10 dex; in the hold-out test (pixels of known value inside cores hidden and predicted), half-width at most 0.10 dex; and the pixel itself at most 8 times above the training range. Its uncertainty is the larger of the 2-4 and 4-8 times values.
  2. Low confidence: the set passes at 2-4 times, but the pixel lies beyond 8 times. Its uncertainty grows with the log of the factor, as the code does now.
  3. Off: the band test fails (more than 0.15 dex), or, for NIRCam, the first-read test fails (median bias beyond ±0.03 dex, or more than 10% of predictions below the saturation level). This switches off the two-filter case: the W51 two-filter set failed with -0.042 dex and 24.8%.
  4. Default: off unless at least three well-spaced filters exist.

What the rule cannot see. All three truths (the brightness bands, the hold-out pixels, the first read) are fainter than real cores, and colours bend at high brightness (hot dust, deeper silicate absorption). A pass therefore holds within the tested range only. The error that grows with depth inside a core (F1000W 0.23 dex low 10-20 px inside the hold-out cores) is not corrected. Agreement with an anchor after pinning holds by construction, so it does not count as a test; the package reports how far the anchor's own fit reaches.

Reading, and what would break.

  • (a) Galaxy nucleus, NIRCam, 2 filters. The first read and the refit run. A few isolated saturated stars get a direct PSF fit; there are too few to train a predictor. The two-filter fill is off by default. An extended nucleus fails the PSF gates, which is the right outcome: it stays empty with a flag. The package needs that "leave it empty and say so" outcome as a first-class result.
  • (b) Protostar, MIRI, 1 filter, subarray. The level-1 correction runs. The response curve needs many pixels of known brightness near saturation; a dark cloud may lack them, and its self-test must then fail loudly. Missing today: subarray detector offsets (the offset map is full frame), the SLOW readout (W51 is FAST) and other group counts (the code assumes 5).
  • (c) Crowded cluster, NIRCam, 3 filters. Many saturated stars make a trained predictor possible. The crowding rules (25 px separation, at most 4 blended stars) break. The cross-filter fill does not apply to stars, which the "kinds it may fill" declaration handles.
  • (d) HII region, 6 or more filters. Everything applies. The number of possible filter sets grows quickly, so the package caps them at 4 features ranked by their band test. MIRI's longest filter needs an anchor: unpinned, the W51 F2100W fill sat 0.13 to 0.37 dex high.

4. What none of the current code handles¶

  • Persistence and cosmic-ray "snowballs". Earlier reports found 14 snowball regions that the star model treated as stars; there is no explicit handling.
  • Charge migration. Restored pixels next to saturated cores carry spilled charge (0.1-0.25 dex in NIRCam first reads and refits); the pipeline only flags it.
  • Brighter-fatter effect. Bright star cores are broader than the PSF model (1% SW, 4-5% LW, 8-22% MIRI in the label validation).
  • Subarrays and other readouts (section 3).
  • Uncertainties for stage 3. The restored uncertainty is in dex; stage 3 weights by variance. The conversion needs a test, and restored pixels from one fit have correlated errors.
  • A second dataset. Every threshold in this report comes from W51. A public benchmark (a W51 cutout plus one other program) is needed before the thresholds can be called general.
  • Licence and citation. A licence file, a citation file, and credit for STPSF, photutils and any anchor data.

5. Shape of the package¶

Where it runs. After stage 2 of the JWST pipeline, on the calibrated (_cal) files, reading the raw groups (_uncal, _ramp) only for the methods that need them. A pipeline-step wrapper can come later; the cross-filter fill needs all filters at once, which a per-exposure step does not see. The package leaves saturation flagging, jump detection, ramp fitting, alignment and mosaicking to the JWST pipeline.

What it writes. A sidecar file per exposure with the restored value, the method (as a name stored in a header table), the uncertainty in dex, and a version and configuration record. A later function writes a copy of the _cal file with restored pixels unflagged and their variance set, so stage 3 can build the mosaic. The current 1/ERR² mosaic stays as a comparison tool.

What it reads from the headers, and what the user supplies. From headers: instrument, detector, filter, subarray, readout pattern, number of groups and frames, group time, whether a first read exists, and the set of filters in the association. From the user, in one configuration file: the input files, which methods to allow (default: all whose self-test passes), the PSF source, any anchor images, and the trust thresholds.

Layout (a sketch):

satrestore/
  io.py          header inference (instrument, readout, filters), loading _cal/_uncal/_ramp
  census.py      kinds of saturated pixels, using the pipeline's saturation flags
  methods/       one module per method: firstread, refit, level1, curve, psf, starmodel, stardiffuse, xfilter, anchor
                 each with: needs(), kinds it may fill, run() -> value, uncertainty, mask; selftest() -> pass/fail and numbers
  merge.py       order and uncertainty rules; border matching
  checks.py      dither checks, hold-out tests, the "what was not restored" report
  cli.py         one command per stage, a configuration file

The agents' effort guesses add up to about 4-5 months of work for 0.1 to 0.3 (0.1: 6-8 weeks; 0.2: 4-6 weeks; cross-filter fill: 5-7 weeks), with large uncertainty.

7. Decisions for you¶

  1. Scope of the first release. The plan above starts with the methods that need no training. Keep that order, or bring the response curve into 0.1?
  2. A second dataset. Which public JWST program with saturated sources should test the thresholds? A sparse field with bright stars and a nearby galaxy would cover cases (a) and (c).
  3. Output. A sidecar file only, or also a modified _cal copy for stage 3 from the start?
  4. Where it lives. A public repository, its name, and its licence (the astropy-affiliated packages mostly use BSD-3).
  5. W51 production. Freeze the current W51 products while the package is built, then rebuild them with the package as its first test?
