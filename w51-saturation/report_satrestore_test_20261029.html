Testing the saturation package on MIRI F2550W¶

This report tests the first version of the package (satrestore/ in this repository) on JWST data outside W51: the MIRI F2550W images of three programs on disk. The package has two versions, as you asked:

  • No training (--mode notrain): methods measured on the dataset itself. The level-1 correction, the first group linearised for pixels flagged only as neighbours of saturated ones, the response curve, and a direct PSF fit for compact saturated regions the curve leaves empty.
  • Training (--mode train): the same, with the PSF values corrected by a star predictor. The predictor learns the PSF fit's error from the program's own unsaturated stars with their brightest pixels hidden.

Every method reports a self-test on each dataset. Where two methods give a value for the same pixel, their agreement is reported too.

Short answer.

  • The no-training version runs on all three programs, whose readouts differ (5, 11 and 20 groups, one or two integrations). Its conversion to MJy/sr reproduces the pipeline exactly where the pipeline has a value.
  • Running on new data exposed three things the W51 code had assumed, now handled by the package:
    • Integrations: the second integration starts from a different detector state, so the level-1 constants differ between integrations.
    • Groups: with many groups, the raw signal at a given charge drifts with the group number, so the curve must come from the early groups.
    • Detector defects: some pixels are flagged as saturated in almost every exposure at fixed detector positions; they are now kept out.
  • Response curve: with 5 groups (cloudc) its self-test matches W51 (0.012 dex near saturation). With 11 and 20 groups it is two times wider (0.026 dex). It now restores only within the range its self-test validated.
  • A second open defect: the "first group linearised" pixels in brick and cloudc are 0.5-0.7 dex too low (section 4): they need the per-pixel saturation level and a self-test.
  • An open defect: in ngc6334 the restored values alternate between even and odd detector rows by about 0.026 dex, and more even rows fall outside the validated range. The calibration pixels never have a saturated first group, so their self-test cannot see this; it needs a group-0 row-parity term.
  • PSF fit: it agrees with the response curve to 0.004 dex on the brick stars where both give a value, once fits that do not look like a point source are refused.
  • Training version: in its own cross-validation it halves the PSF error. On the real saturated stars of brick it moves the values 0.09 dex away from the curve. The learned correction does not carry from the fainter training stars to the brighter saturated ones, so the no-training version is the safer default.

Glossary

term meaning
saturated pixel a pixel that collected more charge than the detector records; the pipeline gives no value when even its first group saturated
group one of the successive reads of the detector during an integration; MIRI reads every pixel up to 20 times here
integration one ramp of groups; brick has two per exposure, the second starting after a reset
level-1 pixel a pixel with only its first group below saturation; the pipeline's value from that one group runs low, and the correction removes the bias
response curve how a pixel's raw signal grows past saturation, measured on pixels whose brightness is known; read backwards, it gives the brightness of a pixel saturated in its first group
PSF fit the shape of a star (STPSF, telescope state on the observation date) fitted to the unsaturated pixels around a saturated core
star predictor gradient-boosted trees that learn the PSF fit's error; the only part trained on examples
self-test a test on the dataset itself: values hidden, restored, and compared with the truth
reduced χ² how well the PSF fits the pixels around the core; large when the source is not a point source
detector defect a pixel flagged as saturated at the same detector position in almost every exposure
dex a factor of 10 in log; 0.1 dex is 26%

1. The data¶

All three programs observed with MIRI full frame and the FASTR1 readout. They differ in the number of groups and integrations, which is what the detector methods depend on. A fourth program on disk (sgrb2, F2550W) lacks the _ramp and _rate files the package reads, so it is left out; running the JWST stage-1 pipeline on its _uncal files would add it.

2. The response curve¶

The curve is measured on each dataset's own pixels of known brightness that saturated in a later group, and read backwards for the pixels saturated in their first group. Its self-test hides groups 4 exposures at a time: the curve and the detector offsets are measured on the other exposures, and the hidden pixels are restored from their saturated groups alone. The figure shows the error against how far past saturation the first usable group was (q = 1 at the saturation level).

Reading. Near saturation (q 1-1.26) the half-width is 0.012 dex for cloudc, which has the same 5-group readout as W51, and 0.026 dex for brick and ngc6334. Further past saturation it widens to 0.04-0.09 dex. The biases stay within 0.015 dex near saturation. The first version of the package was two times wider in brick and ngc6334; two changes brought it here:

first version one set of level-1 constants per exposure, curve from groups 2 to G-2 0.052 dex 0.037 dex

What still separates brick and ngc6334 from cloudc is the scatter of the raw signal about the curve: about 220 DN in ngc6334 and 400-550 DN in brick, against 170-200 DN in cloudc. The detector offsets are smoothed over 8 pixels; offsets that vary from pixel to pixel would need many more exposures per pixel than these datasets have.

Restoring only what was tested. The curve flattens toward its top, so a small error in the raw signal there becomes a large error in brightness. The package restores a pixel only if its first usable group lies within the q range where the self-test half-width stays at or below 0.1 dex: up to q = 1.58 in cloudc and brick, 2.82 in ngc6334. Beyond it the pixel stays empty (34,778 target rows in ngc6334).

The row-parity defect. In ngc6334 the curve values of even and odd detector rows differ: each restored value against the mean of the rows above and below is +0.025 dex on even rows and -0.027 dex on odd rows, and 26% of the even-row targets are restored against 37% of the odd-row ones. The detector offsets have a row term (even rows 224 DN below odd ones), measured on the calibration pixels' later groups. The targets rely on their saturated first group, which no calibration pixel has, so a different parity offset there goes unseen by the self-test. A fix needs a measurement that sees the first group: the balance of restored even and odd rows, or the same sky in other exposures.

The level-1 correction passes its self-test in all three (half the pixels with several good groups fit the constants, the other half predict their brightness from the first group alone): median within 0.004 dex, half-width 0.007-0.010 dex, and within 0.005 dex for the brightest tenth. In brick and cloudc an integration has too few such pixels for its own fit, so the constants are pooled over the exposures, separately for each integration.

3. The PSF fit, and when it can be trusted¶

The PSF fit restores compact saturated regions the curve leaves empty (beyond the top of the curve). Two checks decide whether its values can be trusted:

  • Self-test: bright unsaturated stars of the same images with their 1 to 63 brightest pixels hidden, fitted, and compared.
  • Real saturated stars: where the curve also gives a value, the two are compared.

A fit is refused when its reduced χ² exceeds 5 (with a 5% error floor per pixel). In the first runs, fits above that disagreed with the curve by 0.1-0.3 dex (extended sources, not stars), and fits below it agreed to 0.002-0.02 dex. A region is also fitted only if at least half of a 3-pixel ring around it is measured: regions cut by a detector edge or by an area with no data cannot be fitted reliably.

  • Self-test (left). The direct fit recovers hidden cores to 0.004-0.005 dex in cloudc (2,639 stars), 0.011-0.024 dex in brick and ngc6334 once 7 or more pixels are hidden, and 0.05-0.07 dex in brick when only 1-3 pixels are hidden (a few stars). In ngc6334 the direct fit scatters more about the curve (half-width 0.19 over 358 pixels, many of them on extended emission) and the trained correction narrows that to 0.12.
  • Why the two tests disagree for the trained version. The training stars are unsaturated, so they are fainter than the saturated ones, and their hidden pixels sit closer to measured pixels. Trees do not extrapolate: for brighter stars they apply the correction learned at the edge of the training range, and in brick that correction is wrong by 0.09 dex. The cross-validation cannot see this, because it never leaves the training range. Only the comparison with the curve on real saturated stars shows it.

LAB = {1: 'level-1 corrected', 2: 'first group linearised', 3: 'response curve', 4: 'not restored', 5: 'PSF fit', 7: 'detector defect'}

def best(t, code_, half):
    best_ = (0, None)
    for f in sorted(glob.glob(f'{O}/{t}_notrain/*_satrestore.fits')):
        m = fits.getdata(f, 'METHOD')
        lab, n = ndimage.label(m == code_)
        if n:
            sz = ndimage.sum(m == code_, lab, range(1, n + 1)); i = int(np.argmax(sz))
            if sz[i] > best_[0]:
                cy, cx = ndimage.center_of_mass(lab == i + 1); best_ = (sz[i], (f, int(cy), int(cx)))
    f, cy, cx = best_[1]
    return f, (slice(max(cy - half, 0), cy + half), slice(max(cx - half, 0), cx + half))

Reading. The brick star shows the methods in rings: the saturated core restored by the response curve (blue), one PSF pixel at its centre (orange), level-1 corrected pixels outside (grey). Between them sits a ring of pixels restored as "first group linearised" (green), and it is visibly too dark: these pixels lie 0.47 dex below the good pixels within 2 px of them in brick, 0.73 dex in cloudc, and 0.02 dex in ngc6334. The method treats a pixel whose first group stayed below a uniform saturation level (56,660 DN) as flagged only because a neighbour saturated; MIRI's saturation level varies from pixel to pixel, so some of these pixels did saturate, and their linearised value is a lower limit. This method has no self-test yet, which is how the error got through. In ngc6334 the restored core shows the row-parity defect of section 2 as stripes, and the deepest part of the core stays empty: it lies beyond the curve's tested range.

6. What to decide¶

  1. Default version. The no-training version agrees with the curve on real saturated stars; the training version improves only its own cross-validation. I suggest the no-training version as the default, and the training version kept as an option that reports the comparison with the curve, so its users see when it moves real stars.
  2. The first-group-linearised pixels. Decide with the per-pixel saturation level from the CRDS reference (the W51 cache holds the file these data used), and add a self-test against neighbouring pixels; until then the method should be off.
  3. The row-parity defect. Add a first-group parity term to the curve, calibrated on the balance of restored even and odd rows, and test it on the same sky in other exposures.
  4. The remaining curve scatter. Per-pixel detector offsets would narrow the brick and ngc6334 curve from 0.026 dex toward cloudc's 0.012 dex, but need many exposures per pixel; a pooled offset map across programs of the same detector is a possible next test.
  5. The empty pixels of ngc6334. 185,000 pixel-integrations there are beyond the top of the curve and too extended for a PSF. The cross-filter fill would be the method for them, if the program observed other filters of the same field.
  6. Next data. A NIRCam program with saturated stars would test the first read, which these MIRI data cannot.
